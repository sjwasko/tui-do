# What this session did

`/superpowers:requesting-code-review` over the whole codebase, four scoped reviewers in
parallel (api, store+sync, ui, binary+config+quickadd). Every finding below was
independently verified before it was acted on, and every fix has a test that was watched
to fail without it.

## The four that were shipped and wrong

1. **A pull deleted archived projects and everything in them.** `GET /projects` omits
   archived projects unless `is_archived=true` is sent — the parameter reads like a filter
   and is an *inclusion*. That listing feeds `retain_projects`, which deletes what it does
   not name and cascades to tasks. Not contained by `Reach`: both reaches call
   `pull_lists` unconditionally, which is why all the careful reasoning about what only a
   `Full` pull may delete did not cover it.

2. **Every task write sent `"reminders": []` and the server obeyed.** Measured on dev: one
   reminder in, zero out. Nothing stored reminders, `Task` serialises every field, so a
   store round trip emptied them. Fixed by storing them (`task_reminders`, schema v3).

3. **Every user-facing date was resolved in UTC.** `quickadd::parse`'s doc says the caller
   passes `Local::now()`; all four callers passed `Utc::now()`. `due today` landed at 23:59
   UTC — 18:59 the same evening at UTC-5 — and `relative_date` compared UTC calendar days,
   so a task due this evening read "Tomorrow" then flipped to "Today" at midnight UTC. This
   is *the* bug cria has and that `quickadd/dates.rs`'s module doc claims to have fixed.
   The parser was always right; only the wiring was wrong. `Model.now` is now
   `DateTime<FixedOffset>` from a single `runtime::now()`.

4. **A rejected write stayed on screen.** The store rolled back, the toast fired, and
   nothing reloaded the list — an edit's push ends at `Pushed`, which returns only
   `LoadPending`, so the contradiction sat there for up to five minutes.

## The smaller ones

- `r` pressed during a running sync was silently dropped: `DELTA_AGAIN` had a code and no
  match arm. The old test compared code *ordering*, which was correct and was not the
  broken property.
- `month()` prefix-matched three letters, so "Decide 3 things to do" became a task called
  "things to do" due 3 December. Its whole-word sibling `month_name` already existed a few
  hundred lines down and its doc comment explains the exact hazard. `month` is deleted.
- `Config::save` used `fs::write` → 0644, and `tui-do migrate` copies a cria token into it.
  Now 0600 at creation.
- **No `tracing` subscriber existed at all**, so every warning in the workspace went
  nowhere — including the one about a world-readable token, which *also* only ever checked
  the token file and never the config. Two independent reasons the user could not be told.
  Logging is now behind `TUI_DO_LOG`, to a file, never stdout.
- `Bucket::created_by` was `Option<UserId>` where the spec says `user.User`. Latent until
  Phase 6 wires `VIEW_BUCKETS`. **The conformance test cannot catch this class** — it
  compares field *names* against the spec, never their types.

## Rule 1's enforcement was overstated, and now is not

`CLAUDE.md` and `tui-do-ui/src/lib.rs` claimed the dependency ban *was* the enforcement and
that the crate "cannot await anything". Not true: `rusqlite`, `reqwest` and `tokio` all
arrive transitively via `tui-do-core`, and `tui_do_core::Store` is a public re-export that
`update` could call and block the render thread with. `use rusqlite::…` will not compile;
`Store::open` would. What actually holds the rule is that `update` is synchronous and
nothing calls a store — now asserted by `a_pure_ui_names_no_io`, which greps the crate's
own source. The crate was clean; the claim was not.

# The thing that changed the architecture: tui-do is multi-instance

Stated this session: **a developer with a fleet of boxes, tui-do on each, all against one
Vikunja.** Each box has its own store; the server is the only shared state. This is now in
`CLAUDE.md` under its own heading and in auto-memory.

It resolved one open question and opened a harder one.

**Resolved:** a reviewer flagged `DEFERRED` transactions and outbox double-drain. Both were
about two processes sharing one SQLite file. Separate boxes, separate stores, local disk —
**closed as non-issues.** (If home directories ever become NFS-shared, reopen them
immediately; SQLite locking over NFS is unsafe and WAL especially so.)

**Opened:** concurrent writers against one server, with nothing to build on.

- Vikunja has **no** concurrency control on tasks. No version, no ETag, and `updated` is
  server-set and explicitly unwritable. There is no conditional write to ask for.
- **A partial body clears every field it omits.** Measured on dev: `POST /tasks/{id}`
  carrying only `id` and `title` cleared description, priority and due date. So "send only
  what changed" is not available either.

Both roads closed is what forces the third: **read, merge, write.** `Task::merge_onto` is a
three-way merge over `before`, `after` and the server's current copy. It does not make
concurrent editing safe — nothing can, without a conditional write — it narrows the window
from "since this box last pulled" to one request.

On a true collision the **user's value wins** and `SyncEvent::Overwrote` toasts it. That was
your decision, taken this session. Refusing would lose what they just typed; overwriting in
silence is how a fleet loses work nobody can account for.

`merge_onto` destructures the server task **exhaustively** on purpose: a new field on `Task`
fails to compile there rather than silently keeping the server's value, which is how a field
quietly becomes uneditable. **If you add a field to `Task`, that is where it will stop you.**

Cost worth knowing: one extra GET per queued `UpdateTask`. A box draining a long offline
backlog now does 2N requests instead of N.

## Two sync bugs the fleet framing promoted from cosmetic to serious

- **A skipped task fell out of the watermark.** A pull leaves a task alone when a change is
  queued for it, and was advancing `LAST_PULL` past it anyway — so the server's copy was
  dropped and never asked for again, since `updated` only moves on the *next* edit. In a
  test scenario the watermark jumped nearly a month past it. On one box that is a stale
  row; on a fleet that stale row is exactly what the next full-body write sends back. Now
  clamped to the oldest skipped `updated`. **Clamped, not frozen** — a stuck entry would
  otherwise wedge the watermark permanently. `LAST_RECONCILE` is deliberately *not* clamped:
  a skipped task was still named by the listing, so the retain claim holds.

- **One stuck change held back the entire queue.** The drain stopped at the first failure,
  on the reasoning that the queue is ordered. It is — *within a task*. Two edits to two
  different tasks have no causal relationship. A failure now blocks its own subject and the
  drain moves on. The test that asserted the old behaviour is replaced by two asserting the
  contract that actually matters.

## The outbox now uses what it always recorded

`attempts` and `last_error` were written from the first commit and read by nothing.

- `attempts` drives backoff via `next_attempt_at` (schema v4), exponential 5s → 15min
  ceiling. `ApiError::retry_after()` already existed with no callers; a 429's `Retry-After`
  now wins.
- `Store::queue_health` reports queued/failing/why. The status line says
  `3 queued (1 failing)` — a count that will not go down reads as progress otherwise.
- **No attempt cap and no dead-letter, deliberately.** A permanent failure is a 4xx, which
  `is_permanent` already rolls back with a toast. What keeps retrying is a 5xx or transport
  error, which may genuinely recover, and discarding someone's edit because a server was
  down for a day is not tui-do's call. Revisit only if you decide otherwise.

# Traps this session walked into, so the next one does not

**The release binary is the one that matters, and it lies to you when stale.** Migrating a
copy of the real store reached v3, not v4 — because `cargo build --release` had run *before*
the v4 migration was written. `CLAUDE.md` warns about this and it still happened. Rebuild
release before any check that runs `~/.local/bin/tui-do`.

**Migration numbering:** the reminders migration was first written commented `// v2` when
there was already a v2. It is v3; the outbox column is v4. Comments corrected, but the
already-pushed commit message for the reminders work says "schema v2" and is wrong.

**`git add -p` is not usable in this environment** (interactive). To split unrelated hunks
in one file across commits, copy the file aside, strip the hunks with a script, commit,
restore. Doing it with `git stash --keep-index` nearly lost work and was pure risk.

**Several coreutils are shadowed in this shell** — bare `wc` and `grep` failed oddly.
`/usr/bin/grep`, `command wc` work.

**The real store migrated cleanly**, verified on a copy: 3,889 tasks, v2 → v4, both new
schema objects present, nothing lost. Your actual
`~/.local/share/tui-do/tui-do.db` is still v2 and untouched; it migrates on your next run.

## Deliberately not done, with reasons

- **No attempt cap / dead-letter on the outbox** — see above.
- **A conflict modal on collision** — considered and rejected in favour of user-wins-plus-
  toast, because it interrupts someone who may not be at that box.
- **Merge is only on `UpdateTask`.** `CreateTask`, `DeleteTask` and the label attach/detach
  entries do not read before writing; they do not need to, but say so out loud if that ever
  looks like an oversight.
