`update` arms, not new sync machinery. `../cria/QUICK_ACTIONS.md` is the
behavioural spec.

## What driving it found this session

Every one of these was a live defect on the release binary, found by hand after
a green suite. The pattern holds: the bugs are in what the tests do not simulate
— two processes, a real terminal, a second project with the same name.

| symptom | cause |
|---|---|
| An edited task vanished from the interface *and* the web UI, having saved perfectly | The edit form showed the project by **name** and re-resolved it on save. Dev has two projects called `Inbox`; an untouched field resolved to the wrong one and moved the task. A name is a label, not a key — the field now resolves only when it was actually retyped |
| Terminal said `4 queued`, interface said `3` | `status.queued` was only ever set from a sync report, never read from the store. The outbox is *shared* — `tui-do add` in another terminal writes to the same one |
| Enter in the description did nothing visible | `rows::wrap` used `split_whitespace`, and `\n` is whitespace. The break was stored and then drawn as a space. Also fixed a multi-paragraph description rendering as one blob in the preview |
| No way to see where you were typing in the form | It drew no cursor at all. A comment claimed the focused label made one unnecessary — true for *which field*, useless for *where in it* |
| `tui-do` reported "command not found" after the rename | `~/.local/bin/tui-do` was a **dangling** symlink to the pre-rename path. A dangling link in `PATH` is indistinguishable from never having installed it |
| The first push to a new Forgejo repo was skipped | `git ls-remote --exit-code` returns 2 for a repo that answers but holds no refs — precisely a freshly created one |

## Measurements worth not repeating

**Vikunja does not require unique project titles.** Measured, not assumed: two
`PUT /projects` with the same title both succeeded (ids 40, 41; both deleted).
So the double `Inbox` is a migration artifact but the *hazard* is not dev-only,
and resolving a project by name is unsafe anywhere.

**A project can now be named by id.** `#12` works wherever a project can be
written: `tui-do add +#12`, the edit form's project field, and
`view.default_project` in the config. That setting is also the target for a task
naming no project. Precedence: the project named → the one on screen → the
configured default → the old "find something called Inbox" guess.

**Sync speed is the server, not us.** 78 pages, ~1s each server-side:

| concurrency | time |
|---|---|
| 1 | 88.2s |
| **8 (current)** | **15.2s** |
| 16 | 16.2s |
| 24 | 26.4s |

The server stops parallelising at 8, so `CONCURRENT_PAGES` is already at the
sweet spot and raising it hurts. **The remaining win is not fetching
everything:** `filter=updated > '2026-08-25T00:00:00Z'` returns **1 page, 18
results** instead of 78 pages. Feasibility is proven; the blocker is that the
pull's retain step needs the full id list to know what the server dropped, and
an incremental pull does not mention unchanged tasks. Proposed design, **not yet
decided by the user**: `r` = push + incremental pull, with the full reconcile
kept for startup and the periodic timer. It touches the sync invariant
`CLAUDE.md` is explicit about, so it is the user's call.

success.
