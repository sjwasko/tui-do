## The review happened, and was checked rather than trusted

`8556f1c` fixes three findings from the ultra review of the whole Phase 2 diff. It was
written by a session running in parallel under the same session id, so it was **not**
taken on faith. Each fix was verified by reverting it and watching tests go red:

| revert | tests that fail |
|---|---|
| `Mutation::decompose` → `vec![self]` | 3 (`a_create_whose_label_attach_fails_is_not_sent_twice`, `a_pushed_create_adopts_the_server_id_and_keeps_its_labels`, `an_edit_that_changes_labels_sends_them_through_their_own_endpoints`) |
| `is_already_done` → `false` | 2 (`a_delete_the_server_has_already_done_is_not_undone`, `detaching_a_label_that_is_already_gone_is_not_undone`) |
| the `retain_projects` outbox guard | 1 (`retaining_projects_spares_a_task_with_unsent_changes`) |

Two details in that commit are load-bearing and easy to undo by accident:

- **`decompose` leaves the `UpdateTask` entry label-neutral** (`after.labels =
  before.labels`). `discard_all` rolls back newest-first and `upsert_task` replaces a
  task's *whole* label set, so if the task mutation kept the new labels its rollback
  would clobber the separately queued label entries' work.
- **`settle_create` inserts the server's row before re-pointing `task_labels` /
  `task_assignees` at it, and deletes the provisional row last.** SQLite cascades a
  delete but not an update, and deleting first would cascade away links that exist only
  locally — such as a label attached by an entry queued behind the create.

The review also *suggested* putting the same outbox guard on the `projects` DELETE.
That was correctly declined and should stay declined: `outbox.subject_id` holds **task**
ids, so the subquery would spare whichever project happened to share a number with a
pending task.

## What Phase 2 decided, so it is not relitigated

| | |
|---|---|
| Pseudo-projects | Stored (the sidebar wants Favorites), excluded by `ProjectFilter::default()` (a write-target picker must not offer them) |
| A project's views | An empty `views` from a listing means "not loaded", never "none" — only `set_project_views` honours empty. Fetched on demand, not in every pull |
| Label ownership | Stored (`labels.created_by_id`, migration v2). Vikunja only lets a label's creator edit it |
| Created tasks | Get a provisional **negative** id immediately; `settle_create` swaps in the server's row and retargets whatever was queued behind it |
| Undo | The inverse of a `Mutation`, queued like any other change. Not a parallel mechanism. Undoing a delete *re-creates* — Vikunja has no undelete |
| Labels vs assignees on a write | Assignees are the task body (`UpdateTask` carries them); labels get their own endpoints. `Mutation::decompose` splits a task write carrying label changes at queue time, so callers still just set labels on a task |
| One entry, one request | An entry that took two calls could half-land, and a retry would duplicate a create or re-delete a label. The split happens where entries are written, so the push loop never asks what already happened |
| A 404 meaning "already done" | Not a rejection. Deleting a task another device deleted first, or detaching a label already gone, completes silently. Narrow: a 404 on create means the *project* is missing, which is a real rejection |
| A failed push | Stops the queue. It is ordered, and later entries assume earlier ones landed |
| A 4xx | Final: roll back, and take everything queued behind it *for that task* — those were built on a state the server refused |
| An unreadable response | Treated as transient. It may mean the write landed; a duplicate task is an annoyance, a lost one is a bug report |
| A pull | Never overwrites or deletes a task with unsent local changes — in `retain_tasks` *and* in the `retain_projects` cascade. Each has a test that fails without its guard |
| `retain_labels` | Never deletes a label a stored task still carries. The task proves the label exists, and the cascade would strand a task the pull skipped |

- **The outbox has five mutation kinds** — task create/update/delete and label

  earlier build still parses.
- **Saved filters** have a table and no code. `tui-do-api` has no `SavedFilter` model yet
  either; Phase 6 is where they matter.

Still open, still not blocking: `deploy/seed-from-prod.sh` is bash, so it bypasses the

to runtime. Moving seeding into `tui-do` as a subcommand would put it back under the guard.

## Running things

### The live tests

```sh
cd ~/code/tui-do
./run-live-tests-token.sh          # scoped API token; also accepts a token file as $1
./run-live-tests-password.sh admin # username + password: the only path that exercises
                                   # POST /login and the refresh cookie
```

Both prompt with `read -s`, hardcode the dev URL, and run from the repo root (they resolve
their own directory, so an absolute path works too). `tests/live.rs` takes an **allow**-list:
the URL must match `TUI_DO_DEV_HOST` and prod is refused with no variable that can
countermand it. Without `TUI_DO_TEST_URL` every live test reports success without doing
anything, so `cargo test --workspace` stays green offline.

**The token must be created on the dev instance's own web UI.** A prod token against dev
fails every authenticated call with code 11, "missing, malformed, expired or otherwise
invalid token provided", while `/info` keeps working because it is anonymous — which reads
exactly like a client bug and is not one. Both instances run v2.5.0 with the same seeded
data, so the two web UIs are indistinguishable; check the URL bar.

`connect()` sweeps leftover fixtures before every test, so **each live run writes to dev
even before its assertions**. A token run took 35s for seven tests.
