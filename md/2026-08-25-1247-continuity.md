## The architecture question, answered on the record

**`tui-do add` writes to the local store first, then pushes.** `Store::queue` applies the
mutation locally and queues it for the server in one transaction; the CLI then runs a
push and reports. It shares the parser, the task builder and the outbox with the `a` key.

The decisive reason is **ordering**: the outbox is an ordered queue, and a write that goes
straight to the server jumps it. Add a task from a shell while an edit is queued in the
interface and a direct write lands first — possibly before the create of the task that
edit belongs to. The second reason is that the wire facts in `CLAUDE.md` are encoded once.

The one place local-first was genuinely worse — resolving a name against a cache that may
be empty — is now handled by asking the server, and only when a name matches nothing.

## Load-bearing, do not undo by accident

Beyond the five listed in the previous note (query correlation, selection by `TaskId`,
tri-state panes, exclusive modals, one keymap table), Phase 4 adds:

- **Every edit goes through `update::edit`**, which pushes the inverse and clears redo.
  A mutation applied by any other path silently breaks undo.
- **`Effect::Apply` is the only write effect.** The model applies it to its own snapshot
  first so the next frame shows it; the reload afterwards is confirmation, not mechanism.
- **`SyncEvent::Pushed` exists because a push can be the whole pass.** Without it the
  header sits on "sending" for ever after the first edit.
- **`flush_on_exit` aborts the running pass before pushing.** A pull that stops early
  leaves the store stale and self-heals; a push racing a pull's `retain` can have its new
  task deleted.
