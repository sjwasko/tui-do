## Phase 4 is finished

The quick keys were the whole of what was left, and they are built:

| key | does | modal |
|---|---|---|
| `p` | set priority | a constrained field, 0–5, with a hard limit |
| `D` | set due date | status-line prompt, prefilled, parsed live |
| `m` | move to project | picker, filtered to `id > 0 && !archived` |
| `l` | add or remove labels | multi-select, Space toggles, Enter applies |
| `Space` | configured quick actions | menu of `quick_actions`, the key applies it |

All of it routes through mutations that already existed — `UpdateTask`,
`AttachLabel`, `DetachLabel` — so it was keymap, modals and `update` arms rather
than new sync machinery. `config::QuickActionKind` was parsed and converted out
of a cria config from the start, with tests, but nothing ever *read* it, so a
user migrating from cria had their quick actions silently dropped until now.

Three decisions inside that are worth not re-litigating:

**`l` is bound to the list, not globally**, where every other task key is
global. `l` already means "expand" in the sidebar and that is the vim meaning
nobody should have to unlearn. The cost is that `l` does nothing while the
*preview* has focus; `:` reaches it by name from anywhere. Do not "fix" this by
taking the sidebar's `l`.

**Priority is a field, not the fuzzy picker.** It was a picker first, and
fuzzy-matching a number is nonsense: `0005` matched none of the six rows, so
Enter had no candidate and did nothing at all — and a hard limit and a broken
key look identical from outside. The limit is now on the *keystroke*: only a
digit, and only one that leaves `0`–`5` or `00`–`05` behind, ever reaches the
field. The edit form's Priority field takes the same limit, in place of
accepting any text and reporting "not a priority between 0 and 5" on save.

**A label quick action toggles** rather than only adding. That is what
`QuickActionKind::Label`'s own doc comment says and it differs from cria's
`QUICK_ACTIONS.md`, which says "adds". Deliberate.

## Waiting on you

None of these block Phase 5. All three are reversible.

**1. Incremental sync — measured, designed, undecided since 2026-08-25.** The
pull is 78 pages at roughly a second each server-side:

| concurrency | time |
|---|---|
| 1 | 88.2s |
| **8 (current)** | **15.2s** |
| 16 | 16.2s |
| 24 | 26.4s |

The server stops parallelising at 8, so `CONCURRENT_PAGES` is already at the
sweet spot and raising it hurts. The remaining win is not fetching everything:
`filter=updated > '2026-08-25T00:00:00Z'` returns **1 page, 18 results** instead
of 78 pages. Feasibility is proven. The blocker is that the pull's retain step
needs the full id list to know what the server dropped, and an incremental pull
does not mention unchanged tasks. Proposed: `r` = push + incremental pull, with
the full reconcile kept for startup and the periodic timer. It touches the sync
invariant `CLAUDE.md` is explicit about, which is why it is yours and not mine.

**2. Due dates in the past are allowed, and warn.** `D` accepts `27/08/2024`,
because overdue is a real state and backdating something you have been carrying
is a real thing to want. It is not confirmed quietly, though: the toast is
warning-coloured and says "that date has passed", because a quiet "Due 2 years
ago" would bless `2024` typed where `2026` was meant. The status line shows the
same thing before Enter, in the overdue colour. If you would rather it refuse
outright and need a flag to override, that is a small change — `set_due` in
`crates/tui-do-ui/src/update.rs`.

**3. The help modal now scrolls at 40 rows.** Five new bindings pushed its
content past the fold, so `?` opens with `j/k scrolls` in the title and
`q  Quit` below it. That is E4's documented pass condition in part one rather
than a regression, but the modal is 64 columns wide on a 120-column terminal, so
a two-column layout would fit it unscrolled. A design change, so your call.

## Phase 5 — what it is, and what it needs decided first

From `PLAN.md`:

- **Markdown descriptions via `glow`** (`glow -s dark -w <width> -`), cached per
  task, re-rendered on width change, ANSI parsed back into ratatui spans. `glow`
  is an external Go binary, so it sits behind a `trait MarkdownRenderer` with a
  `pulldown-cmark` fallback — not for Windows' sake, but so tui-do degrades
  gracefully where `glow` is not installed (it is in the Arch repos and Omarchy,
  but not in Ubuntu 26.04's default set). Config `markdown_renderer: glow |
  builtin | auto`, default `auto`.
- **The task detail screen**, comments, attachments including terminal image
  preview, subtasks and relations, and URL extraction/opening.

Questions a design document has to answer before any of that is written:

1. **`glow` is a subprocess, so it is an `Effect`.** Rule 1 says the render loop
   never awaits I/O, and shelling out is I/O. The renderer trait cannot be
   called from `view`; the effect runtime runs it and the result arrives as a
   `Msg`. That means a cache keyed by (task id, width) living in the model, and
   a decision about what to draw while it is still rendering.
2. **Does `Enter` open the detail screen?** It is currently `OpenTask`, which
   shows the preview and moves focus to it. You originally asked for a
   dive-into-task-detail screen, and this is the phase that adds it, so the
   binding is up for re-decision. `Screen` is `#[non_exhaustive]` with one
   variant today and a comment saying Phase 5 adds the second.
3. **Relations** — cria has them half-built and disabled. `PLAN.md` says do it
   properly or not at all.
4. **Terminal image preview** is a capability question (kitty, sixel, none) and
   belongs behind the same platform trait seam as URL opening and the clipboard.
5. **`tui-do doctor` does not exist.** Phase 5's plan references it as the thing
   that reports which markdown renderer is active. It has to be built, or the
   plan reworded.

## What driving it by hand found this session

The pattern holds: the bugs are in what the tests do not simulate — a short
terminal, a shell, a project with a space in its name.

| symptom | cause |
|---|---|
| `0005` in the priority field did nothing, and the key looked broken | It was a fuzzy picker. `0005` matched none of the six candidates, so Enter had no candidate to submit and returned "consumed" |
| Arrow keys in the priority field "did nothing" | They worked the whole time. Every list modal is sized to its content and then clipped by `centered` to whatever the terminal has, and the bodies **truncated instead of scrolling** — so on a short window the highlight walked off the bottom edge with nothing left on screen to show it had moved |
| The project pane would not scroll | The sidebar carried an `offset` from the first day and **nothing ever wrote to it**. `draw_sidebar` honoured it; `update` never set it |
| A shrinking tree drew an empty pane | Found while testing the above: when the selection vanishes with the tree, the first version of `keep_sidebar_visible` returned early and skipped the clamp |
| `tui-do add +Dinner Places …` filed under "Dinner" | A token ends at the first space. `+[Dinner Places]` has always worked and nothing said so |
| A task fetched from a list could not have a pulled label removed | The label form's universe was `data.labels`, but a pull stores tasks and labels in separate passes, so a task can carry one that table has not caught up with |

## Measurements and rules worth not repeating

**Dates are read day-first, then month-first, then year-first**, and the first
reading that names a real day wins. That is what lets `27/08/26` and `8/27/26`
both mean 27 August without either being the house style: only one of them can
be read day-first, so the other falls through on its own. Day-first leads
because it is what Vikunja documents and what the web UI shows, so a genuinely
ambiguous `08/09/26` is 8 September in **both** clients rather than one day here
and another there.

The cost, which is real and permanent: **`YY/MM/DD` is only reached when the two
readings ahead of it are impossible.** `26/08/27` is 26 August 2027, not 27
August 2026. Those are the same three numbers and only one reading can win.

Also supported now: the military `27aug26`, reached by splitting on the boundary
between digits and letters when there is no separator at all; four-digit years
leading; two-digit years pivoting where `strftime` puts them (`68` is 2068, `69`
is 1969); months as `jan`, `sept` or `september`; the spaced `27 august 2026`.
The digit/letter split is the risky part, because it puts `p3`, `v1.2.3`,
`covid-19` and `3rd` in front of the date code for the first time — there is a
test asserting none of them come back a date, and B8 checks it by hand.

**Do not share `CARGO_TARGET_DIR` with a git worktree.** Yesterday's
intermediate commits were verified in throwaway worktrees pointed at the main
`target/`, which baked the worktree path into the cached conformance test binary
as its `CARGO_MANIFEST_DIR`. This morning five conformance tests failed against
a directory that no longer existed. `cargo clean -p tui-do-api` fixes it; not
doing it in the first place is better.

**`tui-do add` writes to the real store.** A `--offline` test task went into
`~/.local/share/tui-do/tui-do.db`, the running instance shared that outbox,
pushed it to dev and adopted id 3944. It was deleted from dev through the API
and both server and outbox are clean. Point a scratch `TUI_DO_CONFIG` at a
scratch store when testing `add`.

**D1 is unexplained and unreproducible.** Reported 2026-08-27: `a` a task, and
the list showed it twice — once as a provisional row (negative id, drawn as
`#-050`) and once adopted (`#2093`). By the time it was investigated the server
held one task, the store held one row and the outbox was empty.
`settle_create` deletes the provisional row inside the same transaction that
upserts the server's copy, so the *store* can never hold both; that points at
the model, where `adopt` retargets the row in `model.data.tasks` and reloads. A
reload landing out of order with an adoption is the shape to look for. If it
happens again, note whether a sync was running and whether `r` had just been
pressed.
