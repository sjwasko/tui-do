## What this is

tui-do is a fork-in-spirit of [cria](https://github.com/frigidplatypus/cria), a Rust/ratatui
TUI client for [go-vikunja](https://github.com/go-vikunja). Upstream has been unresponsive
for months to issues and direct messages, so this is a real fork, not a contribution track.

**Read `PLAN.md` first** — it is the approved plan and the authority on phases and scope.
`CLAUDE.md` carries the working rules *and* the wire-format findings, which are the most
expensive knowledge in this repo. This file only covers what has actually happened.

Predecessor checked out at `../cria` for reference. **Do not copy its code**: it carries no
license (`LICENSE` was never committed in its entire history) and its architecture is what
tui-do exists to replace. Read it to learn *what* a screen shows or *how* quick-add behaves.

### Running the live tests

Two runner scripts at the repo root, both prompting for the credential with `read -s` so it
never reaches a command line, shell history, or disk:

```sh
./run-live-tests-token.sh          # scoped API token; also accepts a token file as $1
./run-live-tests-password.sh admin # username + password: the only path that exercises
                                   # POST /login and the refresh cookie
```

Both hardcode the dev URL. `tests/live.rs` takes an **allow**-list: the URL must match
`TUI_DO_DEV_HOST` (default `sw-surface.tail9803a5.ts.net`) and the prod hostname is refused
with no environment variable that can countermand it. Without `TUI_DO_TEST_URL` every live
test reports success without doing anything, so `cargo test --workspace` stays green offline.

`connect()` sweeps leftover fixtures (projects titled `tui-do live test`, labels titled
`tui-do-live-test`) before every test, so **each live run writes to dev even before its
assertions**. That is deliberate — a failed run orphans fixtures and the next run cleans up.

## Hard-won findings

**All the wire-format findings now live in `CLAUDE.md`** under "Wire-format facts the spec
does not tell you" — zero-time dates, `null` collections, path-vs-body binding order,
pseudo-projects, assignees-vs-labels. Read that section; do not rediscover them.

Three further facts established this session that are *not* in `CLAUDE.md`:

**The spec is authoritative for paths, not methods or bodies — three counts, all decided
in the server's favour.** `PUT /migration/vikunja-file/migrate` is documented `post`;
`POST /tasks/{taskID}/comments/{commentID}` documents no request body but requires one
(proven by the live round-trip's comment edit); `repeat_mode`'s prose disagrees with its own
enum. Only live tests catch this class.

**A project view is not a plain task list — it carries a filter.** The default List view
filters `done = false`, so a completed task vanishes from it. This cost a confusing live
failure that looked like dropped assignees. `tests/live.rs` now asserts it deliberately;
Phase 6 builds Kanban and filter views on these endpoints.

**Vikunja's refresh token is a cookie, not the JWT.** `POST /user/token/refresh` answers
"No refresh token provided." without it, so reqwest's `cookies` feature is a requirement.
The jar is in memory only, so a JWT session does not survive a restart — a deliberate
default, and a decision Phase 2 has to make consciously if sessions should persist.

## Rules that matter (full text in `CLAUDE.md`)

1. **The render loop never awaits I/O.** `tui-do-tui` has no `reqwest`/`rusqlite`/`tokio`
   dependency and must never gain one — that ban *is* the enforcement.
2. **No `show_x_modal: bool` fields.** `enum Screen` + `Vec<Modal>`.
3. **No endpoint not in `spec/vikunja.json`.** Enforced twice now: `tests/conformance.rs`
   checks `endpoints::ALL` against the spec, and `Client::resolve` refuses at runtime any
   template not in that list.
4. **Pagination is never assumed.** Cap from `/info`, pages from `x-pagination-total-pages`.
5. **Writes are optimistic**, with rollback on `Msg::SyncFailed`. **Not built yet** — the
   `outbox` table exists and is empty of code.

Workspace lints deny `unwrap`, `panic`, `todo`, `dbg!` and forbid `unsafe`. Tests `allow`
them at module level; production code may not. A PostToolUse hook runs rustfmt and clippy
on every Rust edit — note it keys off the Edit/Write tools, so **edits made through Bash
heredocs do not trigger it**; run `cargo clippy --workspace --all-targets` by hand.

## Suggested next step

Finish Phase 2, in this order:

1. **Projects and labels in the store** — same shape as `store/tasks.rs`, straightforward.
   Remember pseudo-projects (`id < 0`) must be filterable out of anything offering a write
   target.
2. **The outbox and sync engine** — the interesting one, and rule 5's mechanism. A local
   mutation writes the task row and its outbox entry in one transaction (`Store::write`
   already gives that atomicity, and a test asserts the rollback). The engine drains the
   outbox, and on rejection rolls the row back and emits `Msg::SyncFailed`. Unit-test the
   whole loop against `wiremock`, then live against dev with `reset-dev.sh` between runs.
   Undo/redo rides on this mechanism later rather than a parallel one.
3. **`tui-do migrate`** wiring in the binary, on top of `config::migrate`, which is done and
   tested but not yet reachable from the CLI.

Then Phase 3, which is first light for the TUI. `PLAN.md` calls for `/code-review ultra`
before Phase 3 — worth doing, since Phase 2 is the layer everything else stands on.

Two loose threads worth a glance, neither blocking:

- **A token run took 119s against 20s for the identical password run.** Possibly per-request
  API-token validation server-side. Only matters if it persists once the sync engine starts

- **`deploy/seed-from-prod.sh` is bash**, so it bypasses the `endpoints::ALL` conformance
