# tui-do — TUI design direction, Phase 3

Agreed 2026-08-24, before any `tui-do-ui` code was written, and **implemented the same
day** in `9f98138` and `3474734`. This is the design; `PLAN.md` remains the authority on
phases and scope, and `CLAUDE.md` on the rules and the wire format. Where the build
learned something the design got wrong, it is marked **⟶ built** below.

## The four decisions

| | chosen | over |
|---|---|---|
| Layout | Persistent project sidebar, auto-hiding on narrow terminals | cria's list-first + picker modal |
| Task detail | Preview pane in Phase 3, full `Screen::Task` in Phase 5 | full-screen only; preview only |
| Keys | Vim motions plus cria's leader keys (`Space` quick actions) | cria-compatible first; fresh design |
| Landing | Last project, falling back to all open tasks | Today/Upcoming; all open; Inbox |

## The screen

```
┌ tui-do ─────────────────────────────────────────── ⟳ synced 2m ago ─┐
│ Projects        │ Work › List  Table  Kanban                       │
│  ★ Favorites  6 │ ─────────────────────────────────────────────────│
│  ▸ Work      12 │  Title                    Project  Labels    Due │
│  ▾ Personal   4 │  Fix auth bug             Work     bug     ! 3d  │
│    · Errands  2 │ ✓Renew passport           Personal admin   Sep 2 │
│  ▸ Archive      │                                                  │
├─────────────────┴──────────────────────────────────────────────────┤
│ 42 tasks · 3 queued   ?:help  /:search  g:go                       │
└────────────────────────────────────────────────────────────────────┘
```

Four regions, all persistent: **header** (breadcrumb, view tabs, sync indicator),
**sidebar**, **main**, **status line**. The view tabs (`List Table Kanban`) render from
Phase 3 with only List reachable — Phase 6 *is* the views API, and this strip is where it
lands.

The status line is not decoration. "Server unreachable, 3 edits queued, still responsive"
is the whole thesis of this rewrite and must be legible at all times. It is driven off
`Msg::Tick`, so the spinner turns without anything awaiting.

### Panes are tri-state, not booleans

Each optional pane holds `PaneState { Auto, Shown, Hidden }`. A resize re-evaluates only
panes still in `Auto`; once the user toggles one it stays where they put it. The breakpoints:

| width | Auto resolves to |
|---|---|
| ≥ 120 | sidebar + list + preview |
| 100–119 | sidebar + list |
| < 100 | list only |

This is the responsive rule, not three layout modes: there is one `view` that reads two
pane states and a width.

### Sidebar content, Phase 3

Favorites, then the project tree — nested, expandable, each row carrying an open-task
count. Saved filters get their section in Phase 6, where the API model exists. Labels are
not a sidebar section; label filtering goes through search and the picker, because a label
is a predicate over a list rather than a place to be.

## The model

```rust
pub struct Model {
    screen:    Screen,             // which view of tasks is showing
    modals:    Vec<Modal>,         // stack; the top owns the keyboard
    focus:     Focus,              // Sidebar | List | Preview
    pending:   Option<Prefix>,     // g… and Space… mid-chord
    data:      Snapshot,           // what the store last answered with
    query:     Query,
    query_id:  QueryId,            // monotonic; see below
    layouts:   Vec<ColumnLayout>,  // from ViewConfig::effective_layouts()
    layout_ix: usize,
    status:    Status,             // sync state, queued count, toasts
    theme:     Theme,
    keymap:    Keymap,
    size:      (u16, u16),
}
```

`update(&mut Model, Msg) -> Vec<Effect>` stays pure and synchronous. `view(&Model, &mut
Frame)` only reads.

**Query correlation is in from commit one.** Every `LoadTasks` carries a monotonically
increasing `QueryId`; `Msg::TasksLoaded { id, .. }` whose `id` is not the current one is
dropped. Holding `j` down the sidebar otherwise races the store and lands results out of
order. Four lines now, a heisenbug later.

**Selection is a `TaskId`, never an index.** A reload that reorders or drops rows must not
move the cursor to a different task. The index is derived at render time; if the selected
id is gone, the cursor falls to the nearest surviving row.

### Screens and modals

```rust
enum Screen { Tasks(TasksScreen) }              // + Task(TaskId) in Phase 5;
                                                //   Kanban/Table/Gantt in Phase 6
enum Modal  { Help, Search(..), Picker(..), Confirm(..) }
```

Modals are **exclusive**: the top of the stack receives every key except quit and resize,
with no fall-through to the screen. cria's 790-line dispatch grew out of "sometimes it
leaks." A modal is pure state behind a `ModalView` trait whose handler returns
`Consumed | Dismiss | Emit(Msg)` — it never mutates the world, it asks `update` to.

### Messages and effects, Phase 3

```rust
enum Msg { Key(KeyEvent), Resize(u16, u16), Tick,
           TasksLoaded { id: QueryId, tasks: Vec<Task> },
           ProjectsLoaded(..), LabelsLoaded(..), CountsLoaded(..),
           StoreFailed(String), Sync(SyncEvent) }

enum Effect { LoadTasks(QueryId, Query), LoadProjects, LoadLabels,
              LoadCounts, PersistLastProject(ProjectId), Quit }
```

`crossterm` stays a dependency for its key *types* only — it is not I/O. `reqwest`,
`rusqlite` and `tokio` remain banned, and that ban is the enforcement mechanism.

## Keymap: one table, two consumers

```rust
pub struct Binding { keys: &'static [Key], action: Action, ctx: Context,
                     group: Group, doc: &'static str }
pub const KEYMAP: &[Binding] = &[ /* … */ ];
```

`update` dispatches key → `Action` through it; the help modal renders the same slice,
grouped. They cannot drift because there is only one of them. `Action` being a stable name
is also what makes user rebinding a config change later rather than a rewrite.

```
j k        move                 /  search
g g / G    top / bottom         n  new task            (Phase 4)
C-d C-u    page                 e  edit                (Phase 4)
Tab        cycle pane focus     d  toggle done         (Phase 4)
H L        previous / next column layout
z s / z p  toggle sidebar / preview
g p        go to project        g l  go to label
Space …    configured quick action                     (Phase 4)
?          help, rendered from the table above
```

Two conflicts, resolved deliberately:

- **`H`/`L`** are cria's layout switchers, not vim's screen-top/bottom. cria's meaning
  wins; the vim meaning is reachable as `g g` / `G`.
- **`g`** is a prefix (`g g`, `g p`, `g l`), not an action. `G` alone is bottom.

Prefixes and `Space` quick actions share one mechanism: `Model::pending`. A chord in
flight shows in the status line and any unbound second key cancels it silently.

## Rendering ⟶ built as `rows::measure` and `rows::render`

Pure: `measure(&ColumnLayout, width) -> Vec<MeasuredColumn>` does the width arithmetic and
`render(&[Task], &columns, ctx) -> Vec<RenderedRow>` does the wrapping, returning cells as
`Vec<Line>`. Neither needs a terminal, which is what the golden tests exercise.

- A wrapped row is capped at **3 lines** so scrolling stays predictable.
- Only the **visible window** is laid out. A 1,900-row query must not re-wrap 1,900 titles
  to draw thirty of them. (The design also called for a cache keyed on
  `(query_id, layout_ix, width)`; laying out only the window turned out to make it
  unnecessary, so it was not built.)
- The full result set does live in the model — ~1,900 open tasks is a couple of megabytes
  and makes scrolling free. A hard cap of 10,000 rows keeps a pathological query from
  eating the process, and the status line says so when it bites.

**The width rule changed under test.** The documented algorithm — minimums, then grow
capped columns to their maximum, then share the rest — puts the labels at twenty columns
on a 110-wide terminal while the title sits at its minimum and wraps to three lines. What
ships instead: every column that can still grow grows by the *same* amount, and whatever a
capped column cannot take falls to the title. Both the documented worked example and the
narrow case come out right.

Widths are measured with the same `unicode-width` ratatui draws with, so the width this
crate computes for a column and the width ratatui paints it at cannot disagree.

## Sorting

The active layout's `sort_keys()` is the single source of order — that is why it lives on
the layout. `Column → Option<TaskOrder>` is a partial mapping: `Labels`, `Assignees`,
`Status` and `PercentDone` have no store-side ordering and therefore cannot carry a
`sort:`. Sorting happens in SQL, not in the model, so it never disagrees with the store's
own idea of `NULL` dates. A config that sorts by an unsortable column is a warning at load
and an ignored key, not an error.

## Theme

A `Theme` of semantic slots — surface, text, muted, accent, selection, `priority[1..=5]`,
due overdue/soon/later, done, label fallback, ok/warn/error — with `vikunja-dark` as the
default and `vikunja-light` shipped beside it. Label colors arrive from the server as hex
and get a contrast-aware foreground rather than a fixed one. `NO_COLOR` is honored, and
truecolor → 256 → 16 degradation sits behind the platform trait that the macOS port will
also use.

## States that must render before data does

Launching against a cold store still paints the chrome. The body shows `Loading…`, not an
empty table that reads as "you have no tasks". A store error is an inline banner in the
main pane, never a modal — the rest of the interface still works. Offline is a status-line
state, not an error.

## What Phase 3 needed from `tui-do-core` ⟶ built

All additive, no schema change:

- `Store::project_task_counts() -> ProjectCounts` — one grouped query, not a count per
  project. The sidebar redraws whenever the store changes and thirty round trips through
  `spawn_blocking` to paint a column of numbers is thirty too many.
- `TaskFilter::favorite`. The sidebar's Favorites row cannot be answered by
  `project: Some(-1)`: Vikunja *presents* favourites as a pseudo-project but the tasks
  keep their real `project_id`, so it is a column predicate.
- The remaining column-backed `TaskOrder`s — start date, updated, status, percent done —
  so the sortable/unsortable line falls where the reason is (a task column can sort; a
  join cannot) rather than where the enum happened to stop.
- `sync_state` holds the last project under a `ui.` prefix. A migration to hold one
  string would have cost more than the prefix that keeps the namespaces apart.
- `tui_do_core::models` re-exports `tui_do_api::models`. `tui-do-ui` names `Task` constantly
  but must not depend on the crate carrying `reqwest`, because that dependency list *is*
  the enforcement mechanism for rule 1.
- `Store::default_path()`, honouring `$TUI_DO_DB`. The database is a cache that can be
  deleted and rebuilt, so it lives in the data directory, not the config one.

## Testing

- `update` driven by `Msg` sequences with assertions on `Model` — no terminal, the point
  of the split.
- `TestBackend` golden files at **80×24, 120×40, 160×50**, which are exactly the three
  breakpoint bands.
- `layout_rows` tested directly: width distribution, wrap capping, truncation with `…`.

## The command palette ⟶ built after all

`:` opens a fuzzy palette over the keymap, listing what each command does with its key
right-aligned beside it — so running something by name teaches the binding for next time.
It was written off as "possibly never" in the first draft of this document and turned out
to cost about forty lines, because three decisions already made paid for it: `Action` is a
stable name decoupled from its key, `PickerState` already did fuzzy matching, and every
binding already carried a `doc` string.

Two details worth keeping:

- **A command by name runs the same `act(model, action)` as its key.** There is no second
  dispatch path, so the two cannot disagree about what "toggle the sidebar" means.
- **A candidate carries a `Pick`, not an `i64`.** `Pick::Project(ProjectId)`,
  `Pick::Label(LabelId)`, `Pick::Command(Action)` — a command picker cannot submit a
  project id, where an id plus the picker's kind to interpret it would have made that a
  runtime possibility for no gain.

Motions are excluded — typing four letters to move down one row is not a command, and six
motion entries would crowd out what is worth searching for. So is the palette itself.

## Search filters as it is typed

`/` opens a prompt on the **status line**, not a panel in the middle of the screen — a box
would cover the list it is filtering. Every keystroke re-queries the store and the results
narrow underneath, with a live match count beside the prompt. Enter puts the prompt away
and keeps the filter; Esc restores whatever was showing before the search opened, which is
not the same as clearing it.

This cost almost nothing to add because the expensive part was already built. Firing a
query per keystroke is only safe if late answers cannot land out of order, and that is
exactly what `QueryId` has done since the first commit. The store answers a `LIKE` over
3,877 rows in about 2ms, off the render loop.

## Narrow terminals are a first-class case

Two rules, both found by driving it rather than by thinking about it:

**Room is one decision.** `PaneState` says what the user *wants*; `geometry::frames` alone
decides whether it fits. A second width rule on `PaneState::Shown` is what made `z p` set
a pane that never appeared, with nothing on screen to say why. A pin is now honoured
wherever it fits — the preview reaches 90 columns with the sidebar up, 70 without.

**A refusal is told, and told something actionable.** The sidebar is laid out first, so on
a middling terminal it is usually the sidebar rather than the width standing between the
user and a preview; "widen the terminal" would be true and useless. A toast owns the whole
status line for the same reason — sharing it with the key hints cut the advice in half.

**The header degrades in a fixed order**: view tabs first, then the brand. What survives to
45 columns is the breadcrumb and the sync state, because "which list is this" and "is it
talking to the server" are the only two questions the header answers that the rest of the
screen does not. Golden files at 45×20 hold that line.

## Deferred, on purpose

Full task detail and comments (Phase 5), per-project layout memory, mouse support.

`view.default_filter` is **read and ignored**, which is worth knowing before someone
"fixes" it: it holds a Vikunja filter expression such as `done = false && priority >= 3`,
and the local store answers a title substring. Wiring one to the other would silently
return nothing. Filter expressions arrive with saved filters in Phase 6, through the views
API that evaluates them.

## What running it taught

Two defects that no test had, both found by looking at a screen:

- A status message longer than the terminal walked straight over the key hints.
  `view::fit` now cuts the message and never the hints.
- The preview rendered raw HTML. "Descriptions are shown as stored" sounded reasonable
  when it was written here and means `<p><a target="_blank" rel="noopener"` on screen
  against real data. `rows::plain_text` is the stopgap; Phase 5 still owes it `glow`.
  **Correction, 2026-08-30: `rows::plain_text` is gone and so is `glow`.** Descriptions
  render through comrak + html2text now — see
  `md/2026-08-30-markdown-descriptions-design.md`.

And the thesis, confirmed end to end against the dev instance: pointed at an unroutable
address so the connection hangs rather than refusing, tui-do renders 1,935 cached tasks,
takes motion keys, and quits cleanly while the connect is still pending.
