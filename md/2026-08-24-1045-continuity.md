## What this is

criax is a fork-in-spirit of [cria](https://github.com/frigidplatypus/cria), a Rust/ratatui
TUI client for [go-vikunja](https://github.com/go-vikunja). Upstream has been unresponsive
for months to issues and direct messages, so this is a real fork, not a contribution track.

**Read `PLAN.md` first** — it is the approved plan and the authority on phases and scope.
`CLAUDE.md` carries the working rules. This file only covers what has actually happened.

Predecessor checked out at `../cria` for reference. **Do not copy its code**: it carries no
license (`LICENSE` was never committed in its entire history) and its architecture is what
criax exists to replace. Read it to learn *what* a screen shows or *how* quick-add behaves;
its `tests/` are a useful behavioural spec.

## Hard-won findings — these cost real time, do not rediscover them

**Vikunja encodes "unset" dates as Go's zero time**, `"0001-01-01T00:00:00Z"`, not `null`,
because its SQL columns are `NOT NULL`. Parse naively and every dateless task reads as 2000
years overdue. The spec is no help: every timestamp is a bare `{"type":"string"}` with no
format. All of this is handled in `models/datetime.rs`; route new date fields through it.

**Two upstream spec bugs found. Where spec and server disagree, the server wins.**
1. `PUT /migration/vikunja-file/migrate` — the spec declares `post`; the server answers 405
   with `Allow: OPTIONS, PUT`.
2. `repeat_mode`'s prose says the third variant is `3`; the enum and `x-enum-varnames` in the
   same document both say `2`. The enum is authoritative.

The spec is ground truth for **paths**, but is not infallible about **methods**. Only live
integration tests catch that class of error.

**Postgres 18+ changed its mount convention** — data lives in a version subdirectory
(`.../18/docker`), so the volume must mount `/var/lib/postgresql`, *not*
`/var/lib/postgresql/data`. The image refuses to start otherwise.

**Vikunja defaults `VIKUNJA_FILES_BASEPATH` to `/app/vikunja/files`**, which the container's
uid cannot write; it crash-loops until pointed at the mounted `/db`. Also use
`VIKUNJA_SERVICE_SECRET`, not the deprecated `VIKUNJA_SERVICE_JWTSECRET`.

**Export status is `GET /user/export`** returning `{id, created, expires, size}` where `id` is
0 until built. It is **not** on `GET /user` — `user.User` has no export field at all.

**`percent_done` is a fraction (0.0–1.0), not a percentage**, despite the name.

## Deviation from the approved plan — already made, flagged, not yet overruled

The plan called for generating models from the spec. **They are hand-written instead.** The
spec under-describes the wire format in ways codegen cannot recover from (the timestamp
problem above), so generated types would be `String` fields plus a hand-written conversion
layer — the same work, one indirection further from the truth. Drift detection, the actual
point of codegen, is covered better by `crates/criax-api/tests/conformance.rs`, which checks
model fields against the spec *and* catches fields we have stopped modelling.

Both conformance failure modes were verified by deliberately breaking them: reintroducing
`/tasks/all` fails two tests, adding an unknown model field fails a third.

If the user prefers codegen after all, that is a live option — the deviation was flagged, not
approved.

## The rules that matter

1. **The render loop never awaits I/O.** `criax-tui` has no `reqwest`, `rusqlite` or `tokio`
   dependency and must never gain one — that ban *is* the enforcement.
2. **No `show_x_modal: bool` fields.** `enum Screen` + `Vec<Modal>`.
3. **No endpoint not in `spec/vikunja.json`.** Add it to `endpoints.rs`; the test checks it.
4. **Pagination is never assumed.** Read `x-pagination-total-pages` /
   `x-pagination-result-count`; take the cap from `/info`'s `max_items_per_page`.
5. **Writes are optimistic**, with rollback on `Msg::SyncFailed`.

Do not weaken the prod-write guards to make something pass.

## Credential handling

`seed-from-prod.sh` prompts for passwords and keeps them in shell variables only — never on a
command line (where `ps` would show them) and never on disk. **The user runs it; the assistant
does not handle those credentials.** Preserve that property in anything that replaces it.

`seed-from-prod.sh` is bash, so it bypasses the `endpoints::ALL` conformance guard — which is
exactly how the `POST`-vs-`PUT` bug survived to runtime. Moving seeding into `criax` as a
subcommand would put it back under that guard. Worth doing eventually; not urgent.
