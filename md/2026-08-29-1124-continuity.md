## What shipped on 2026-08-28

Eight commits. The three decisions the last note parked, two defects the manual checks
found, one design document, and shell completions.

**`r` fetches only what changed; `R` fetches everything.** A pull of dev is 78 pages and
15 seconds; the same pull filtered to what changed is one page. `sync::Reach` names the
two and **only `Full` may delete** — a filtered listing does not mention what did not
change, so retaining against it would erase all but the last few days of the user's tasks.
Startup and the timer stay full. What `r` cannot see is a deletion made in another client,
so it names `R` in its toast at the keystroke.

Two things inside that were not in the parked proposal and matter:

- `LAST_PULL` and the new `LAST_RECONCILE` are separate keys. An incremental pull can say
  "everything up to here has been seen" without being able to say "and nothing else is
  gone".
- The watermark is stamped from **before** the requests, and the filter reaches a further
  two minutes back. The watermark is this machine's clock and `updated` is the server's;
  a few seconds of disagreement would drop a task in the gap *permanently*, because the
  next pull asks from an even later point.

**The help modal folds into two columns** when one column would be clipped and the
terminal is wide enough. At 80 columns it goes back to scrolling and says so. The fold
only ever lands on a heading, so no section is cut across the gutter; the empty space
under the shorter column is that rule's price.

**Past dates are said loudly on all four ways in.** This was the B9 failure. The rule was
implemented once, on `D`, and there are four surfaces: `D`, the edit form's Due field,
quick-add, and `tui-do add`. The other three answered "Saved", "Added" and nothing —
exactly the quiet confirmation the rule exists to prevent. `past_due_note` is now the rule
in one place. The edit form warns only when the save *moved* the date and compares **by
day, not by instant**: the field shows a date and the parser gives it 23:59, so an
untouched form re-parses 09:00 into 23:59 and an instant comparison would call every save
of anything overdue a backdate.

**`d` holds its place down a list, the way `x` does.** Reported by hand, became E6. `x`
moves the selection to the row that slid into the gap; `d` queued an `UpdateTask` that
replaced the row in place, left the selection on a task the reload then dropped, and
`TasksLoaded` cannot tell "the selected row left this list" from "this is a different
list" — so it fell back to the first row and every press sent the cursor to the top. Now
the row leaves at the keystroke and the selection steps down. Undo still works: every
`Effect::Apply` is followed by a reload, which is what returns the row.

**Shell completions.** `tui-do completions <bash|zsh|fish>`, generated from the same
command table `--help` is built from. See the caveat below about what this actually buys
on this workstation.

## Creating labels: designed, not built

`md/2026-08-28-label-creation-design.md` is the whole of it. Four places in the interface
say "tui-do cannot create labels yet" and `PLAN.md` assigns fixing it to no phase. The API
half is done and live-tested; what is missing is `Mutation::CreateLabel`, and rule 5 means
that variant *is* the write path.

**The decision the document exists for**, because it is cheap now and expensive after the
first `CreateLabel` is written: `Mutation::subject()` returns a `TaskId` and
`outbox.subject_id` is an untyped `INTEGER`, load-bearing in five places including the
guard that stops a pull from deleting a task created offline. Provisional task ids count
down from `-1`; a label counter would too, so task `-1` and label `-1` would be the same
value in the same column — and `retain_tasks` and `settle_create` both break without
saying anything. Recommended: a `Subject { Task, Label }` enum and a `subject_kind`
column. The two alternatives and why they lose are in the document.

Two further findings in it: adoption has more holders for a label than for a task, and the
easy miss is an open `Modal::Labels` whose state holds cloned labels; and the rejection
blast radius has to widen, because the `AttachLabel`s that must die with a rejected
`CreateLabel` are queued against the *task*, so same-subject filtering will not find them.

**Three things need measuring against dev before any of it is written**, none answerable
from `spec/vikunja.json`: what a duplicate label title does, whether `PUT /labels` with
`id: 0` has the path-versus-body trap, and what a replayed create answers — there is no
`is_already_done` arm for it.

## Waiting on you

Only two are real decisions. Neither blocks Phase 5.

1. **Does label creation get built, and how much?** Create-only, or rename, recolour and
   delete too. Deleting is the one `u` cannot cleanly undo — the label returns with a new
   id and detached from everything it was on.
2. **Should `*newlabel` in quick-add create the label silently?** Everywhere else the user
   is looking at a label list and asking for a new one. In quick-add they typed a task, and
   a typo becomes a permanent label on the server. Silent, confirmed, config-flagged, or
   not in quick-add at all.

Low-stakes and defaultable: where creating a label appears in the UI, and which phase owns
it — it is a Phase 4 gap found after Phase 4 was signed off.

## Phase 5 — unchanged, and still needs a design document first

From `PLAN.md`: markdown descriptions via `glow` behind a `trait MarkdownRenderer` with a
`pulldown-cmark` fallback; the task detail screen; comments; attachments including
terminal image preview; subtasks and relations; URL extraction and opening.

The five questions a design document has to settle are unchanged from the last note:

1. **`glow` is a subprocess, so it is an `Effect`.** Rule 1 means the renderer cannot be
   called from `view`. That implies a cache keyed by (task id, width) in the model, and a
   decision about what to draw while it is still rendering.
2. **Does `Enter` open the detail screen?** It is `OpenTask` today. `Screen` is
   `#[non_exhaustive]` with one variant and a comment saying Phase 5 adds the second.
3. **Relations** — cria has them half-built and disabled. `PLAN.md` says properly or not
   at all.
4. **Terminal image preview** is a capability question (kitty, sixel, none) and belongs
   behind the same platform trait as URL opening and the clipboard.
5. **`tui-do doctor` does not exist** and Phase 5's plan leans on it as the thing that
   reports which markdown renderer is active. Build it or reword the plan.

## Environment notes worth not rediscovering

**This workstation runs bash, and only bash.** fish and zsh are not installed. Completions
are installed at `~/.local/share/bash-completion/completions/tui-do` and bash-completion's
lazy loader picks them up. The greyed-out inline suggestion that prompted the work
**cannot happen on bash** — it belongs to fish's autosuggestions or the zsh-autosuggestions
plugin, and bash has no equivalent. Completions still buy Tab completion of subcommands
and flags, which is worth having.

One loose end there: clap generates the `complete` spec with `-o bashdefault -o default`,
so bash still falls back to filenames when the completion function returns nothing. The
`ValueHint::Other` on the task text does its job in fish and zsh but is overridden by
those options on bash, so `tui-do add <TAB>` still lists the working directory. Fixing it
means patching clap's generated script, which was not done.

**Do not share `CARGO_TARGET_DIR` with a git worktree** — still true. It bakes the
worktree path into the cached conformance binary as its `CARGO_MANIFEST_DIR`.

**`tui-do add` writes to the real store.** Point a scratch `TUI_DO_CONFIG` at a scratch
store when testing it.

Dev `https://dev-box.example.net:8443` for everything. Prod
`https://prod-box.example.net:8443` **read-only, always** — Forgejo shares that box on
a different port, so pushing git there is not a prod write. **Tailscale has to be up or the
