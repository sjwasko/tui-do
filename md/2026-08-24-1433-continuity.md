## What Phase 2 decided, so it is not relitigated

| | |
|---|---|
| Pseudo-projects | Stored (the sidebar wants Favorites), excluded by `ProjectFilter::default()` (a write-target picker must not offer them) |
| A project's views | An empty `views` from a listing means "not loaded", never "none" — only `set_project_views` honours empty. Fetched on demand, not in every pull |
| Label ownership | Stored (`labels.created_by_id`, migration v2). Vikunja only lets a label's creator edit it |
| Created tasks | Get a provisional **negative** id immediately; `settle_create` swaps in the server's row and retargets whatever was queued behind it |
| Undo | The inverse of a `Mutation`, queued like any other change. Not a parallel mechanism. Undoing a delete *re-creates* — Vikunja has no undelete |
| Labels vs assignees on a write | Assignees are the task body (`UpdateTask` carries them); labels get their own endpoints. `Mutation::decompose` splits a task write carrying label changes at queue time, so callers still just set labels on a task |
| One entry, one request | An entry that took two calls could half-land, and a retry would duplicate a create or re-delete a label. The split happens where entries are written, so the push loop never asks what already happened |
| A 404 meaning "already done" | Not a rejection. Deleting a task another device deleted first, or detaching a label already gone, completes silently. Narrow: a 404 on create means the *project* is missing, which is a real rejection |
| A failed push | Stops the queue. It is ordered, and later entries assume earlier ones landed |
| A 4xx | Final: roll back, and take everything queued behind it *for that task* — those were built on a state the server refused |
| An unreadable response | Treated as transient. It may mean the write landed; a duplicate task is an annoyance, a lost one is a bug report |
| A pull | Never overwrites or deletes a task with unsent local changes — in `retain_tasks` *and* in the `retain_projects` cascade. Each has a test that fails without its guard |

## The premise that was unverified is now settled

`Sync::pull` stores what `GET /tasks` returns and then deletes every local task the
listing did not mention. If the server omitted **done** tasks, one pull would erase the
user's completed history.

**Verified live on dev, 2026-08-24 ~14:45.** The unfiltered listing returned 3,877 tasks
of which 1,942 were done, and `filter=done = true` returned exactly those same 1,942 with
none missing. Recorded in `CLAUDE.md` under the wire-format facts.
`tui-do-api/tests/live.rs::an_unfiltered_task_listing_includes_done_tasks` keeps it honest
and reports "inconclusive" rather than passing quietly if dev ever holds no done tasks.

All 7 live tests pass. The full run also settled a second question it raised: with 4
labelled tasks but only 1 label in `/labels`, it was not obvious whether that listing
covers labels that appear only on tasks. `retain_labels` no longer depends on the answer
— it never deletes a label a stored task still carries, since the task proves the label
exists, and cascading the attachment away would strand a task the pull skipped for having
unsent changes. The live test now prints the two sets and their difference, so the next
run says which it is either way.

Running the live tests needs a token created **on the dev instance's own web UI**. A prod
token against dev fails every authenticated call with code 11, "missing, malformed,
expired or otherwise invalid token provided", while `/info` keeps working because it is
anonymous — which reads like a client bug and is not one.
